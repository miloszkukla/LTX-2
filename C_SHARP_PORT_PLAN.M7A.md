# Remote single-GPU .NET 10 LTX-2 port

## Summary

- Port the single-GPU LTX-2 stack to C# targeting `net10.0`/Linux CUDA; retain Python side-by-side as the seeded numerical oracle until parity is signed off. Use .NET 10 LTS, not .NET 11 preview. [Official .NET lifecycle](https://dotnet.microsoft.com/en-us/platform/support/policy)
- Work entirely on disposable Vast.ai Linux instances. The local agent only provisions and monitors the remote work, and uses its authenticated local `gh` CLI solely to register/revoke remote-generated deploy keys and read the redacted remote-status branch: at each milestone it verifies that the reported commit SHA exists on the fork, reviews the redacted health/build/test artifacts against that milestone's acceptance criteria, and confirms that source changes are pushed and the instance contains no uncommitted source work before destruction. The remote Codex agent performs all edits, builds, tests, commits, and pushes locally on the Vast host; SSH is only an occasional bootstrap/recovery control channel and never carries the transpilation, build, test, or GPU workload.
- Use a 32 GB FP8-capable instance for routine work and the parallel post-M6 text-to-video delivery sample, plus a separate lowest-cost compatible single 80 GB A100 or H100 instance only for standard-profile validation. Prefer A100 80 GB when BF16/VRAM validation is sufficient; use H100 80 GB only for Hopper-specific native FP8 coverage. Multi-GPU, B200-specific paths, DDP/FSDP, CUDA IPC/all-to-all, `*_mgpu` pipelines, and full fine-tuning are deferred.

## Dependency and implementation decisions

| Existing dependencies | .NET decision |
|---|---|
| `torch`, `torchaudio`, `numpy`, `einops`, `scipy`, `transformers`, `accelerate`, `natten`, `mps-sdpa` | Fork TorchSharp/LibTorchSharp against LTX's PyTorch 2.13/CUDA 13.2 ABI; port model logic and tensor operations. Do not mix the stock TorchSharp CUDA runtime with LTX's ABI. |
| `nvidia-cutlass-dsl`, Triton, FlashAttention, `bitsandbytes`, `optimum-quanto`, `peft` | Build `libltx_cuda.so` plus C# bindings for in-scope, non-B200 single-GPU kernels, quantization, and LoRA. There is no adequate managed substitute; B200-specific Blackwell DSL and all multi-GPU paths remain deferred. |
| `safetensors` | Implement `Ltx.SafeTensors` read/write compatibility against the published format schema. [Safetensors schema](https://github.com/huggingface/safetensors/blob/main/docs/safetensors.schema.json) |
| `av`, `imageio`, `imageio-ffmpeg`, Pillow/HEIF, OpenCV, OpenImageIO, `soundfile`, `torchcodec` | FFmpeg.AutoGen, OpenCvSharp, ImageSharp, and a small native OpenImageIO bridge; preserve MP4, EXR/HDR, image, and audio behavior. |
| `pydantic`, YAML, `typer`, `rich`, `tqdm` | System.Text.Json, YamlDotNet, Ookii.CommandLine, and Spectre.Console. |
| Hugging Face, GCS, OpenAI, Google GenAI, Weights & Biases | Official .NET HTTP/SDK clients; retain a narrow W&B HTTP adapter. No real external API calls in parity tests. |
| `pytest`, `ruff`, `pre-commit`, `matplotlib`, CUDA build tooling | `dotnet test`, analyzers/format checks, BenchmarkDotNet only for diagnostics, and CMake/NVCC for native builds. |

Create `Ltx.Core`, `Ltx.Pipelines`, `Ltx.Trainer`, `Ltx.Media`, `Ltx.SafeTensors`, `Ltx.Cuda`, and `Ltx.Cli`, plus an LTX-maintained TorchSharp/LibTorchSharp fork. Preserve `.safetensors`, LoRA, model-layout, and `ltx` CLI compatibility; add compatibility launchers where existing users depend on Python command shapes. Existing Python trainer checkpoints are not resumed by C#; new C# runs produce their own resumable state.

## Remote Vast.ai and Codex workflow

0. After the initial instance, deploy-key registration, fork clone, and remote Codex installation, but before implementation work, the local manager transmits this plan's complete text and SHA-256 to the remote Codex bootstrap prompt. The remote agent writes the received plan to `C_SHARP_PORT_PLAN.md` and creates `PORT_STATUS.md`; both are included in the single accepted M0 commit on `codex/ltx-csharp`, and the remote plan copy must hash-match the bootstrap prompt. This is the only plan handoff; the local manager never commits or pushes source changes.

1. Use the confirmed public fork [`miloszkukla/LTX-2`](https://github.com/miloszkukla/LTX-2). On the remote host, generate an ephemeral SSH deploy key. The manager obtains only its public half through one direct-SSH read, registers it as a write-enabled key with local `gh api`, records the returned key ID in `PORT_STATUS.md`, and verifies one remote push. The private half remains only on the remote host. On recovery or final cleanup, the local manager deletes the recorded GitHub deploy-key ID before registering a replacement or destroying the host; never reuse or export a private key. Clone the fork, add upstream `Lightricks/LTX-2` read-only, and work on `codex/ltx-csharp`. Push every verified milestone from the remote host.

2. Run the local Vast CLI preflight with access to its normal user configuration directory, then confirm `vastai --raw` search/status works. Do not substitute raw API calls. The user approved a $0.60/hour `dph_total` cap for the 32 GB worker and a $1.20/hour `dph_total` cap for the 80 GB validation worker, with no per-instance-duration or total-spend ceiling; enforce the applicable hourly cap and record the unlimited duration/spend authorization in `PORT_STATUS.md`. Select live offers by total hourly price, reliability >=95%, direct SSH availability for bootstrap/recovery only, and sufficient host RAM; remote Codex's implementation workload runs locally on the worker rather than over SSH:
   - Primary worker: lowest-cost compatible 32 GB+ FP8-capable GPU, preferring RTX 5090; user-approved 48 GB Ada fallback; 32 GB+ system RAM and 200 GB disk. Exclude RTX A6000/Ampere because it lacks FP8 support.
   - Validation worker: lowest-cost compatible one A100 80 GB or H100 80 GB, 64 GB+ system RAM and 200 GB disk; use H100 only when the M0 inventory identifies Hopper-specific native FP8 coverage. Record host memory after checkpoint load and recreate with more RAM if less than 8 GB remains available. Create only for standard-profile checkpoints; retain it only until its results are pushed and M8 has downloaded the parallel sample artifact, then destroy it with the 32 GB worker.
   - Exclude B200 and all multi-GPU offers. If no acceptable 32 GB offer exists, use the lowest-cost supported 48 GB Ada-class fallback rather than a 24 GB card.

3. Create each instance with explicit disk, direct SSH, and cancellation-on-unavailability: `--disk 200 --ssh --direct --cancel-unavail`. Vast account environment variables, including the user-provided `HF_TOKEN`, are injected at instance runtime; do not repeat that token in `--env`. M0 starts from `nvidia/cuda:13.2.0-cudnn-devel-ubuntu24.04`; record its resolved Linux/amd64 digest and verify `nvidia-smi`, `nvcc`, compiler, CUDA libraries, disk, RAM, and GPU compute capability before any porting. Accept Linux driver `>=580` only through CUDA 13.x minor-version compatibility: compile native code to SASS for the reported GPU architecture, avoid relying on PTX JIT, and require the M0 CUDA/TorchSharp/native smoke test to pass; destroy the host if that test fails. M0 calculates required model/fixture/cache disk from its artifact manifest; if it exceeds 200 GB, destroy and recreate with that recorded requirement plus 20% headroom before downloading any model. [NVIDIA CUDA image tags](https://hub.docker.com/r/nvidia/cuda/tags?name=13.2.0-cudnn-devel-ubuntu24.04) [CUDA 13.2 release notes](https://docs.nvidia.com/cuda/archive/13.2.0/cuda-toolkit-release-notes/index.html)

4. In M0, add a source-free `Dockerfile.remote`, `.dockerignore`, `scripts/remote/bootstrap-host.sh`, and GitHub Actions workflow that builds `ghcr.io/miloszkukla/ltx-csharp-base` from the recorded NVIDIA image. Before relying on it, the workflow proves it can publish with `GITHUB_TOKEN` and `packages: write`, then sets the package public when permitted and records the result in `PORT_STATUS.md`; it must not use a personal token. Because a first GHCR publish is private by default, acceptance requires an unauthenticated pull by digest from a fresh Vast worker, not only a successful Actions publish. The image contains the pinned CUDA development toolchain, .NET 10 SDK, CMake/Ninja, Git, Python/uv, FFmpeg runtime/development libraries, OpenCV runtime prerequisites, and OpenImageIO runtime/development libraries; record their installed package versions and require an `ldconfig`/P-Invoke smoke test. It excludes the repository source, model weights, fixtures, API keys, deploy keys, Codex authentication, and `HF_TOKEN`. The Dockerfile must not declare `ARG HF_TOKEN` or `ENV HF_TOKEN`; Vast injects it only into a running worker. If publishing, public visibility, or anonymous pull fails, record the exact failure and use the same checked-in bootstrap script directly on the NVIDIA base for every worker; this is a supported, slower fallback, not a blocker. All later workers prefer the verified anonymously pullable digest, otherwise the NVIDIA base plus the bootstrap script. [GitHub Packages billing](https://docs.github.com/en/billing/concepts/product-billing/github-packages) [GHCR workflows](https://docs.github.com/en/packages/working-with-a-github-packages-registry/working-with-the-container-registry)

5. Install remote Codex after each instance is established, using the official Linux installer. Authenticate through user-approved ChatGPT device sign-in; no OpenAI API key is stored on the rental host. Run interactive sessions in persistent `tmux` with Full access: `codex --sandbox danger-full-access --ask-for-approval never`. Run autonomous milestone sessions with `codex exec --sandbox danger-full-access`; `codex exec` is non-interactive and does not accept `--ask-for-approval`. This is intentional for the disposable single-purpose worker: it lets Codex install system/CUDA/.NET prerequisites, use Docker, access build/package caches and the ephemeral deploy key, and run GPU tooling without nested sandbox or approval interruptions. The exposure is bounded by the disposable host, a fork-only ephemeral deploy key, and deletion of the host/key at completion or recovery. [Codex CLI installation](https://learn.chatgpt.com/docs/codex/cli) [Sandbox configuration](https://learn.chatgpt.com/docs/sandboxing)

6. Add version-controlled remote instrumentation before porting: preflight/health scripts, GPU-memory and temperature sampling, CUDA/.NET/native-library version checks, build/test result collection, and a heartbeat containing instance ID, commit SHA, current milestone, current phase, UTC timestamp, and redacted failure reason. M0 emits `artifacts/M0/source-surface.json`, enumerating each Python package/module, CLI entry point/flag, pipeline, and native kernel as in-scope or deferred with a reason. M0 also creates a dedicated `codex/ltx-csharp-status` branch containing only a redacted `heartbeat.json`; a background task force-updates it at least every five minutes, and the local manager reads its commit timestamp through `gh` without accessing source worktrees. The concurrent M7A worker instead uses the same schema on `codex/ltx-csharp-m7a-status`, so its updates cannot overwrite M7B's primary-worker heartbeat. The preflight records only whether a fine-grained read-only `HF_TOKEN` is present, never its value, and performs an authenticated, read-only access probe for every required model/checkpoint before M1; it records artifact revision, size, checksum source, and required disk without downloading model data until the disk gate passes. Model-download commands receive the token only from the running instance environment. Persist redacted manifests and result summaries with each accepted milestone; never log tokens, deploy-key material, or account environment values. If `HF_TOKEN` is visible only to PID 1 rather than the interactive Codex shell, load it transiently for that one download command without printing it or writing it to shell profiles, `tmux` configuration, source files, Docker build arguments, or Git.

7. Use GPT-5.6 Sol at xhigh reasoning for architecture, ABI, and CUDA-kernel work; use Terra at high only for bounded mechanical conversions after interfaces and numerical fixtures are accepted.

## Milestones and failure recovery

Each milestone creates one atomic, pushed checkpoint on `codex/ltx-csharp`. Before that commit, update the tracked `PORT_STATUS.md` with the milestone ID and state, source and fork SHAs, exact verification command, GPU tier, required model/fixture revisions and SHA-256 values, redacted artifact path, known failures, and the next milestone. Commit a compact redacted `artifacts/<milestone>/summary.json` containing toolchain/GPU versions, commands, exit codes, test totals, numerical tolerance results, and artifact checksums. No checkpoint may rely on an artifact that exists only on the instance.

| Milestone | Worker | Acceptance gate |
|---|---|---|
| M0: Remote bootstrap | 32 GB | The remote copy of this plan hash-matches the bootstrap prompt and is committed with `PORT_STATUS.md`; the remote deploy-key public half is relayed once, registered locally with `gh`, and proves a remote push; Codex sign-in, driver/disk/model-access preflight, CUDA/TorchSharp/native SASS smoke test, and a source-surface inventory all succeed; the redacted status branch publishes one heartbeat; GHCR is anonymously pullable by digest from Vast, or the recorded failure selects the checked-in NVIDIA-base bootstrap fallback; `scripts/remote/verify-milestone.sh M0` emits the initial manifest and exits 0. |
| M1: C# foundation and ABI | 32 GB | `Ltx.sln` Release build, LTX TorchSharp/native CUDA smoke test, and the parity-fixture runner all pass. |
| M2: Storage and model loading | 32 GB | Safetensors/LoRA round trips and fixed checkpoint-loader fixtures pass at the recorded tolerances. |
| M3: Core model execution | 32 GB | Transformer, VAE, audio/vocoder, conditioning, and offload fixture suites pass with seeded numerical parity. |
| M4: CUDA, quantization, and LoRA | 32 GB | Every in-scope, non-B200 single-GPU native kernel has a tested correctness path; quantization and LoRA fuse/unfuse fixtures pass. |
| M5: Media and pipelines | 32 GB | Every in-scope non-`*_mgpu` CLI mode from the M0 source-surface inventory passes small seeded video/audio/HDR/EXR fixtures and preserves documented exit/output behavior. |

Every earlier suite passes, real-checkpoint single-GPU pipeline parity and the standard-profile trainer smoke test pass; H100 is required only for Hopper-specific native FP8 coverage; all deferred features are explicitly reported as out of scope. |
| M7B: Text-to-video delivery sample | 32 GB, in parallel with M7A | Prefer the documented `TI2VidTwoStagesPipeline` with the full 22B development checkpoint plus its documented distilled LoRA for quality. If two-stage fails, diagnose and record the precise cause; first retry the duration ladder 10 seconds → 5 seconds → 3 seconds, then reduce resolution. Use the standalone `DistilledPipeline` only when the diagnosed, documented two-stage limit remains 32 GB VRAM after those mitigations, and record why it was selected. Any one-stage failure is likewise a debugging task, not a reason to omit the sample. Then log out of remote Codex, revoke each recorded deploy key, and destroy both Vast instances with `vastai destroy instance <id> -y`; record successful teardown. |

`scripts/remote/verify-milestone.sh <M0..M7A,M7B,M8>` is the sole acceptance entry point. It runs the milestone's prerequisites and relevant tests, writes the redacted summary, and exits nonzero on any missing artifact, version mismatch, failing test, or tolerance breach. The remote agent may begin `M(n+1)` only after `M(n)` is accepted, committed, pushed, and recorded in `PORT_STATUS.md`; M7A and M7B begin in parallel only after M6 is accepted, and M8 begins only after both are accepted.

If the remote-status branch is older than 15 minutes, or Vast reports `exited`, `unknown`, or `offline`, the local manager reads the last pushed `PORT_STATUS.md`, then obtains `vastai show instance <id> --raw` and `vastai logs <id> --tail 100` before any recovery action. For a terminal host failure, delete the recorded GitHub deploy key with local `gh api`, then destroy the instance with `vastai destroy instance <id> -y`; do not attempt to recover uncommitted work. Provision a replacement in the tier named by the incomplete milestone with the recorded GHCR image digest when one exists and is anonymously pullable; otherwise use the NVIDIA base plus the checked-in bootstrap script. Re-authenticate Codex through the user-approved device flow, generate a new ephemeral deploy key, relay only its public half to local `gh api`, register the new key, clone the recorded SHA, run the checked-in bootstrap, restore only model/fixture inputs whose revisions and checksums are in `PORT_STATUS.md`, and rerun that milestone's verification command. If the last checkpoint was not accepted, restart that milestone; if its artifact is missing or invalid, treat it as incomplete. Only user authentication can pause this recovery path.

## Porting and verification

- Port core tensor modules, transformer/VAE/audio/vocoder, checkpoint loaders, LoRA fusion, quantization, and single-GPU custom CUDA kernels first. Provide explicit correctness fallbacks only where Python already has one; do not silently drop unsupported kernels.
- Port every in-scope non-`*_mgpu` pipeline and CLI flag enumerated in the M0 source-surface inventory, including video/audio, conditioning, retake, interpolation, IC-LoRA, and HDR flows. Preserve CPU/disk offload and low-VRAM modes.
- Port preprocessing and single-GPU LoRA training. The 32 GB worker validates the low-VRAM profile; the 80 GB worker validates the standard single-GPU profile. Full fine-tuning remains deferred because the source documents it as a multi-GPU FSDP workload.
- Generate small fixed Python-oracle fixtures for each operator/model boundary. Require FP32 `rtol=1e-4`, `atol=1e-5`; BF16/FP8 `rtol=2e-2`, `atol=5e-3`. Test safetensors round trips, LoRA load/fuse/unfuse, CLI exit/output behavior, media I/O, seeded pipeline outputs, one-step trainer loss/gradients, and native-kernel fallbacks.
- On the 80 GB worker, run real-checkpoint standard-profile parity for each single-GPU pipeline and trainer smoke test. Performance is recorded but is not a release gate.
- After M6, run M7B on the existing 32 GB worker in parallel with M7A. Its cinematic prompt is a continuous golden-hour tracking shot through a rain-wet city street, with a person crossing frame and natural ambient sound; prefer the documented two-stage text-to-video path, full development checkpoint, and distilled LoRA. The 10-second target is a preference, not a pass/fail requirement: diagnose a two-stage failure, follow the recorded duration-then-resolution fallback ladder, and use the standalone one-stage distilled pipeline only if the diagnosed remaining blocker is the 32 GB VRAM limit. Diagnose any one-stage failure rather than dropping the sample. Download the final MP4 with its SHA-256 to the local machine before teardown; do not use a screenshot or a remote-only artifact as the delivery substitute.
- At each accepted milestone, follow the checkpoint protocol, then commit source and tests, push from the remote host, capture the exact SHA in the heartbeat, and retain no uncommitted source work. At final completion, after M7A, M7B, and the local MP4 delivery are verified, log out of Codex, revoke each deploy key, and destroy both instances. No persistent Vast volume is used.

## Assumptions

- The starting reference is commit `400fd31054597515f47125691032c04b1c3ee24e`.
- Current Vast pricing is intentionally not assumed: live selection waits for the local CLI preflight to succeed.
- The writable public fork `miloszkukla/LTX-2` is verified to exist, forked from `Lightricks/LTX-2`, and has `main` as its default branch.
- The user authorized a $0.60/hour `dph_total` ceiling for 32 GB work and $1.20/hour for the 80 GB validation worker, with no per-instance-duration or total-spend ceiling; M0 records this authorization and enforces the applicable hourly cap.
- The configured Hugging Face token is fine-grained/read-only and is authorized for every model/checkpoint selected by the M0 artifact manifest.
- The 32 GB tier handles all feasible development work; 80 GB is reserved for isolated validation gates, not continuous development.
- The public GHCR bootstrap image contains no source, models, fixtures, credentials, or Codex session data; it exists solely to make the toolchain reproducible across disposable hosts.
